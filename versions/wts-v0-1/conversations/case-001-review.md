# WTS 0.1 Case 001 复盘点评

> 本点评只评估对话、工具调用、中间文件和执行结果中的可观察行为，不声称读取了模型的隐藏思维链。完整证据见 [Case 原稿](case-001.md)。

## 一句话结论

Agent 完成了从过载 JD 裁决、目标公司确认到三轮渐进式检索的主链路，且第 3 轮通过“去公司限定 + 切换未试词族”找到了一位强匹配；但评分、反思、Controller 与终态报告的中间记录不完整，导致“为什么这个人 93 分、其他人为什么低于推荐线”无法被完整复核。

## 关键决策链

1. **先缩减 JD，不盲搜**：识别出四条顶级要求叠加，用户裁决为三条必须项，将超节点降为强加分。
2. **用目标公司调研建初始池**：用户选择华为、燧原、壁仞；站内探测证明华为和燧原可用。
3. **第 1 轮失败后拆分过窄查询**：从四词叠加改为主路径搜服务器、第二路单独探索 chiplet。
4. **第 2 轮有召回但方向错位**：没有因头衔或公司背景放宽必须项，判断三人都不是硬件系统架构。
5. **第 3 轮放弃公司限定、改试未覆盖词族**：使用 X86/服务器和超节点/集群双路径，最终找到孙**。
6. **以轮次上限收尾**：不因最后找到一人而超预算继续搜索，转入终态报告。

## 问题与风险

1. **评分不可复核**：第 2 轮和第 3 轮没有完整保存逐人分项分、证据和硬冲突判断。这不是展示问题，而是中间产物缺失。
2. **终态报告没有内部源文件**：未观测到 `report.json`，终态文本中的 93 分无法通过结构化记录追溯。
3. **公司词重复使用**：华为在前两轮都被使用，与“一家只用一次”规则冲突，也浪费了已探测可用的燧原公司词。
4. **5 秒要求只能部分验证**：四份计划都包含 5000 ms，但缺少逐操作计时或完整 runtime 证据，不能将“写入参数”等同于“每个操作确实间隔 5 秒”。
5. **局部可用性瑕疵**：交互参数首次校验失败；最开始的过程播报使用英文，与“用户看到的一律是白话中文”不完全一致。
6. **隐私风险**：原始终态答复包含候选人详情直链。对用户展示可能合理，但进入 GitHub Case 时必须遮盖，本原稿已处理。

## 对下一版的启发

### 建议固化

- 每轮必须落盘一份评分表、反思和 Controller 决策，终态报告只从这些文件渲染。
- 在 SearchPlan 中记录公司词使用历史，Builder 或前置校验直接拒绝重复公司词。
- 将“查询过窄 / 方向错位 / 候选人存量不足 / 页面筛选失效”变成标准反思类型。
- 对操作间隔类要求保存可计算的实际执行时间证据，不只保存计划参数。

### 保持为待验证假设

- “华为 + ODM + AI 芯片厂”是这类人才的典型路径，目前只有一个强匹配样本，还不足以写成通用规则。
- “放宽 15 年或 X86 中的一项”能显著扩大高质量候选人池，本 Case 尚未实际验证。

## 评价边界

- “未观测到”不等于“确定没有执行”；它表示现有会话、文件和工具结果不足以证明。
- “智能涌现”不与“遵循 SOP”混同。部分表现是高质量地执行了已有规则，因此标为“强执行信号”而不是全新能力。
- 候选人评价只复述本次测试中 Agent 的行为，不构成对候选人的独立事实核验。
