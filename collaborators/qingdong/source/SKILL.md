# 猎聘智能寻访

两个阶段，一条**确认门**：先把 JD 拆成需求确认稿并取得用户确认，确认之后才使用浏览器工具；确认后围绕唯一的**主池**按轮次检索，每轮一份 SearchPlan、一次搜索执行、一次隔离评分、一次反思、一次 Controller 决策；停止后输出终态报告，再列出**备选方向**请用户选择。

浏览器由 `scripts/build_workflow.py` 编译出的工作流驱动，Agent 只接触 workflow_ref 和 result_ref；**网络搜索工具**只在步骤 3.5 调研目标公司时使用。

## 与用户交互

### 提问

request_user_input 是**独占调用**：它所在的这一轮里没有别的工具调用。固定 skill_name=wts，step_id 见各步。宿主的字段约束：每题最多 8 个选项；label ≤ 80 字，只放选项本身，理由和差异写在 description（≤ 240 字）；prompt ≤ 300 字；用户可自行填写用 allow_custom=true 表达，推荐的填写值放 custom_placeholder。确认需求时，完整需求稿放在问题的 description；如果超过字段限制，先作为普通文本完整输出，description 只放摘要。prompt 始终只写一句简短问题，不重复正文。

**每次让用户选，都给推荐**——推荐统一写在 label 开头：`[推荐] 选项内容`；所有选项的 `recommended` 字段保持 false（宿主的推荐标记每题只允许一个，且会和前缀重复，所以只用前缀）。单选：一项带 [推荐]。多选：前 3 项带 [推荐]（不足 3 个可选项时全标），按推荐顺序排列。自由填写：custom_placeholder 给推荐值。每个推荐在 description 里附一句依据，推荐就是 Agent 自己判断的公开版本，让用户多数时候只需同意。

**用户看到的一律是白话**：选项、画像、播报、报告都写给猎头看。Agent 的规格和记录（需求确认稿、内部报告）写到任务工作目录 `<TASK_WORK_DIR>/wts/` 下的文件里，给用户的文本是从文件渲染出来的视图；title 范围、公司层、置信度、candidate_ref 等内部字段只在文件和决策记录里出现。

新建文件使用 `write_file`；修正已经存在的需求、计划或决策文件使用 `edit_file`。不要用临时脚本绕过字段校验或回改已经执行的历史计划。

### 播报

检索阶段用户只能看到一连串工具调用。在标有 **播报** 的节点，先用普通文本输出 1–3 句，再发起下一次工具调用；播报是普通文本，不占独占调用。固定说三件事：刚完成了什么、结果的数字、接下来做什么。只说数量和检索关键词；姓名、分数、公司、简历内容只在终态报告出现（步骤 11.3 校准门是唯一例外，且不出现姓名和分数）。

**内部名词不出现在用户面前**。下面这些词只能出现在文件和决策记录里：workflow_ref、result_ref、candidate_ref、detail_ref、SearchPlan、iteration、hard_filters、site_filters、semantic_criteria、decision_basis、candidate_scores、correction_reason、PRF、Controller、Builder、settle、证据文本、主锚点、支持词、词族、待试词、活跃词、备用词。要对用户提到这些概念时用对照表里的白话：主锚点→核心岗位词；支持词/活跃词/备用词→搭配词；待试词→试探词；公司词→公司名；PRF 晋升/拒绝→这个搭配词有用/没用；强匹配→很匹配；可推荐→值得推荐；硬性条件→必须满足的条件；决策记录→我的工作记录。

**工具返回的文本不直接播报**。Builder、宿主、浏览器返回的错误和提示（含"证据文本被改写会被视为修订"这类校验提示）都是给 Agent 的，Agent 按提示修正后只向用户说结果：修好了就不提，修不好就用一句白话说明卡在哪一步、需要用户做什么。播报里不出现原始错误文本、字段名和参数值。

**固定句式**。轮次小结只用下面三句填空，不自由发挥，每句都是完整的陈述句：
1. "第 N 轮看完了：「关键词 A」带来 X 位新人，「关键词 B」带来 Y 位，Z 位是之前看过的。"
2. "目前累计 P 位值得推荐，其中 Q 位很匹配。"
3. 继续："下一轮换「关键词 C」，因为<一句原因>。" / 停止："<一句原因>，我马上整理报告。"

任何停止、暂停或等待用户处理的状态（需要登录或处理验证码、触发风控、致命错误、效果不确定而暂停）先用同一格式播报——发生了什么、需要用户做什么或系统接下来会怎样——再停下。例："猎聘要求重新登录，浏览器窗口已打开，请登录后我会自动继续。"

## 执行 SOP

### 1. 取上下文

从任务上下文取得 JD、职位标题（可能缺失）、目标人数、任务 ID、绝对的任务工作目录、绝对的内置 Skill 目录和轮次预算，直接使用运行时提供的绝对路径。

用户在上一次寻访报告后选择了某个备选方向再发起本次任务时，对话历史里会有那个方向的名称和 title 范围：它就是本次的主池，其余全部从零开始——重新拆解、重新澄清、重新确认。唯一延续的是**已看台账**：对话历史里有上一次报告的 `seen_ledger_path` 时，按 `references/seen-and-expand.md` 把它合并进本次的 `<TASK_WORK_DIR>/wts/seen.json`，这些人本次不再打开详情。

### 2. 拆解需求，形成需求确认稿草案

- **标题锚点**：有职位标题时，从标题提取 1–2 个候选人会在简历里逐字写出的短锚点，去掉"工程师""开发""研发""算法""技术专家"等后缀和公司前缀（"千问-AI Agent工程师"→"AI Agent"；"Flink开发工程师"→"Flink"）。没有标题时从 JD 总结一个岗位锚点并标注"[由 JD 总结]"。第一个锚点是**主锚点**，全程固定出现在每条查询里；第二个是**第二锚点**，只作第 1 轮的搭配词。
- **原子化**：JD 是"尚未验证的需求证据"，逐句拆成独立需求。缺失的写"未指定"并保持未指定直到用户回答；推测标 [假设]。缺失、推测和下面三种病症都汇入待澄清清单，按步骤 3 的主题归类。示例——"需要很强的数据能力，北京上海深圳杭州成都均可"：正确拆法是"数据能力是工程/分析/建模哪种？未指定"、"五个城市是工作地还是来源地？未指定"，两条都进待澄清清单。
- **JD 病症**：很多 JD 是从网上抄来再改的，三种常见病各有固定处理，识别后打标记，处理动作在步骤 3 的对应主题轮执行：
  - **[CONFLICT] 逻辑矛盾**：两条要求在逻辑上不能同时成立（"3 年以上经验"+"资深架构师职级"；"本科"+"博士优先"）。标记后必问，题型是三选一：取前者 / 取后者 / 两条都放宽为加分项。涉及受保护属性的一方按决策规则直接告知不执行，矛盾随之消失。
  - **[过载] 全能型 JD**：每条单看合理，合起来市场上没有人。信号：反事实测试后必须满足仍 > 5 条；必须满足横跨 ≥ 3 个职能；年限与职级明显不配。标记后必问，题型是排序题：Agent 列出自己判断的必须满足名单和降级名单，请用户勾选"缺了就不行"的那几条。
  - **[套话] 模板句**：沟通能力、团队合作、责任心、抗压这类通用句。先试着改写成可观察行为（"跨团队推动项目落地"→ 看项目经历里有无跨部门项目）；改不动的标 [套话]，列入确认稿【备注】供用户捡回。
- **[假设] 的去向**：每个 [假设] 走两条路之一——在澄清轮里问掉，或原样列进确认稿【关键判断】让用户看见。
- **必须满足 / 加分项 / 排除信号**——按用途分类：
  - 必须满足：缺了就做不成岗位，用于搜索和硬筛。判据是**反事实测试**："不满足此条但其余都优秀的人，能否六个月内做成岗位？"答"可能"就降为加分项。重点审查学历、年限、知名公司是否只是能力的代理变量。每条注来源（JD 第 n 条 / 用户确认）。
  - **简历可见性测试**：通过反事实测试的每一条，再问"猎聘详情页的哪个区块能看出来？"（工作经历 / 项目经历 / 技能 / 教育经历 / 自我评价）。答得出来的才留在必须满足或加分项，并记下区块。答不出来的——顶会论文、绩效、口碑、抗压、带团队规模这类简历通常不写的——**不删除也不评分**，进新桶 **面试核实项**（`verify_in_interview`），确认稿和画像里单列一行让用户看见。简历上偶然写了，作为加分项的证据使用，但缺席不扣分。
  - 加分项：确实正确但只进评分。
  - 排除信号：硬过滤。来源：JD 明确不要、用户补充不要、默认排除。默认排除初始只有"近 1 年内多次跳槽"，确认稿中标"默认"，用户可要求去掉。
  - 模糊素质词按 [套话] 处理。
- **硬性筛选条件**：只收 JD 明确写出、且猎聘页面能验证的地点、学历、工作年限、公司、学校类型、工作内容。未声明的默认"不限"；年限、学历、薪资未填写时同样默认不限，是否该成为必须满足由反事实测试决定，需要裁决时归入步骤 3 第 4 轮。
- **检索关键词**：从 JD 提取最多 8 个非锚点**支持词**，只取可能逐字出现在简历里的原子词——技术、工具、框架、算法、方法、稳定的能力名词（"大模型应用落地"不取，"RAG""LangChain"取；"高并发系统建设"→"高并发"）。同一概念的不同写法归为一个**词族**，一个词族只取一个代表词。前 6 个为**活跃词**，其余为**备用词**。公司名是另一类检索词——**公司词**——由步骤 3.5 单独产生和管理，与支持词互不占额。
- **不做搜索词**：薪资、地点政策、流程偏好、抽象素质、受保护属性。它们分别只进硬性筛选、评分项，或完全不用。
- **年龄要求的转换**：JD 或用户写了年龄（"35 岁以下"）时，不估算、不映射、不进任何筛选和评分。它标记为 [年龄→年限]，进待澄清清单，在步骤 3 第 4 轮问用户真实关切是什么，转成工作年限这个页面能筛、简历能验证的条件。

完成标准：主锚点、必须满足、硬性筛选条件、检索关键词四项都有明确内容或明确写着"未指定"；面试核实项已单列；待澄清清单已列出全部"未指定"、[假设]、[CONFLICT]、[过载]、[年龄→年限]，并按步骤 3 的主题归好类；[套话] 已单列。

### 3. 判断是否需要澄清

有效 SearchPlan 至少要有一个明确的主锚点，加上至少一个能区分候选人范围的支持词或硬性筛选条件。仅有"产品经理""技术人员""运营"等宽泛岗位名，加"有技术意识""学习能力强"等软性特质，不算有效搜索锚点；软性特质按 [套话] 处理。

**门禁**——五类必答：岗位与职级、核心技能、必须满足的边界、城市、排除信号。每一类都要有结论（JD 写清了算有，用户答了算有）且没有未裁决的 [CONFLICT]，才进需求确认门。目标公司走步骤 3.5，在此不问。另外三种情形无论如何都要问：任务上下文只有职位 ID/名称而没有 JD 正文；只有宽泛岗位名和软性特质；同一描述存在多个会显著改变关键词或硬性筛选条件的合理解释。

**主题轮次**——澄清按主题分轮，一轮一个主题、1–3 个问题，顺序固定、最重要的先问；JD 已写清的主题跳过；同一主题只问一轮，同一缺口只问一次；上限 5 轮。

| 轮 | 主题 | 触发条件 | 题型 |
| --- | --- | --- | --- |
| 1 | 岗位定位 | 主锚点不清，或有多种解释 | 单选 + 自定义 |
| 2 | 必须满足的裁决 | 有 [过载]，或反事实测试降级了任何一条 | 多选：Agent 给出必须满足名单与降级名单，用户勾选"缺了就不行"的 |
| 3 | 矛盾裁决 | 有 [CONFLICT] | 每条三选一：取前者 / 取后者 / 都放宽为加分 |
| 4 | 城市与硬边界 | 城市未指定、多城市，年限/学历是否算硬条件待定，或有 [年龄→年限] | 城市自由填写；硬边界单选；年龄转换单选（见下） |
| 5 | 排除信号 | JD 没写"不要什么" | 多选 + 默认项 + 自定义 |

城市专项：实际工作地 ≠ 候选人来源地。JD 出现多个城市要问清几个 HC、最终在哪入职、"均可"是各地有团队还是接受搬迁；JD 列出几十个城市时问"是否有重点城市、真实主阵地在哪"。

年龄转换专项：prompt 说明"年龄我不会用来筛人，但通常背后有一个真实关切，我按它来筛"。选项固定四个，label 里给出对应的年限档位（猎聘只支持 1–3、3–5、5–10、10 年以上）：[推荐] 工作年限（如"35 岁以下"→"10 年以内"）、职级/带团队范围、薪资带宽、都不是（自定义说明）。用户选年限就写进硬性筛选条件的 experience_years，来源标"用户确认（由年龄转换）"；选其他就分别进评分项或不用；年龄本身永远不进文件的筛选和评分字段。

每轮调用 request_user_input，step_id=clarify-jd。收到答案后合并进需求确认稿草案，回到步骤 2 只更新受影响的部分，再判断下一主题是否触发。5 轮用完或回答后仍不足以形成有效搜索词时停止并说明缺少什么。

完成标准：五类门禁全部有结论；待澄清清单里没有未处理的 [CONFLICT] 和 [过载]；剩余 [假设] 已标记为待进【关键判断】。

### 3.5 目标公司

城市已确认之后才做这一步，因为调研要按城市找公司。两个分支：

- **JD 已列出目标公司**：照录，每家置信度 1.0，来源标"JD"，跳过调研和提问。
- **JD 未列出**：先用一句白话告知用户（"JD 没有指定目标公司，我先用网络搜索调研一下，再请您确认"），再按 `references/target-company-research.md` 用网络搜索工具调研，产出岗位定位、公司类别和带置信度的公司清单，然后按其提问格式调用 request_user_input，step_id=confirm-target-companies。用户自定义补充的公司置信度 1.0，来源标"用户"；用户勾选调研结果只表示采纳，置信度保持调研值。

**去向**：

- **目标公司**：用户采纳的公司（勾选的调研结果 + 自定义补充）→ 进**目标公司池**，同时进加分项和市场洞察。置信度只用于排序和记录。
- **公司类别**：调研得到的类别本身，写方向不列名 → 进市场洞察。

**目标公司池**是贯穿全程的公司词候选清单，记在决策记录里，每家一行：公司名｜来源｜置信度或命中人数｜探测召回｜可用 / 不可用 / 未探测｜已用 / 未用。两个来源：

- **初始**：本步骤的目标公司。用户自定义补充的排最前（按填写顺序），状态直接标"可用"——用户点名的公司不探测；其后是勾选的调研公司，按推荐顺序，状态"未探测"。
- **扩充**：第 1 轮起，每轮评分后（步骤 11）把**高分候选人**（口径见 `references/scoring.md`）的当前公司和履历中的过往公司加入池子，来源标"高分候选人"，记命中人数；已在池中的公司累加命中人数。这是第 1 轮之后新公司的唯一来源；扩充公司只作公司词和市场洞察，加分项只认初始目标公司。

**公司词**的全部使用规则集中在此：

- **探测只发生一次**，在第 1 轮开始前（步骤 6.5），对象是勾选的调研公司按推荐顺序的前 3 家（不足 3 家就是全部）。首屏卡片数 > 10 为**可用**，≤ 10 为**不可用**。第 4 家起状态保持"未探测"，和不可用的公司一样只服务加分项和市场洞察。
- 每轮主路径最多带一个公司词，一家公司只用一次；第二路永远只有锚点和支持词。选择顺序：先用未用完的自定义公司（按填写顺序，用户点名的最优先）；用完后，第 1 轮取探测召回最高的可用调研公司，第 2 轮起候选是"可用且未用的调研公司"和"扩充公司"两类，由 Agent 选——反思提建议，Controller 拍板——被多位高分候选人命中的扩充公司优先，其余按命中人数和探测召回判断。没有候选时主路径只用锚点和支持词。
- 公司词是检索词而非硬条件——公司进 hard_filters 的唯一途径仍是 JD 或用户明确要求"只要这些公司"。

用户全部不选或选"不限"时目标公司写"不限"，池子初始为空、不探测，第 2 轮起仍按高分候选人扩充；调研得到的岗位定位和公司类别保留给市场洞察。

完成标准：目标公司有明确结论（清单或"不限"）；每家公司有置信度和来源；目标公司池已按推荐顺序建好。

### 4. 需求确认门

写确认稿之前先完成两件事：

- **城市分层**：城市 A=实际工作地/主池，B=可搬迁来源，C=仅观察不入池。
- **主池与备选方向**：**主池**是 Agent 判断最可能的方向 = 精确 title × 目标公司 × 城市 A 层，是本次 1–3 轮检索唯一服务的对象。**备选方向**是 Agent 判断"不是最可能、但也有可能"的其他解释——相邻 title、相邻行业、可迁移背景、B 层城市的组合——最多 2 个，每个一行写清名称、title 范围、与主池的差别。备选方向只记在决策记录里，在步骤 16 呈现；确认稿只写主池。主池拿不准时把它当作待澄清项在步骤 3 问。

然后按 `references/requirements-draft.md`：把需求确认稿写成 `<TASK_WORK_DIR>/wts/requirements/vN.json`，从它渲染**候选人画像**，做完决策无损核对后先以普通文本输出画像，再调用 request_user_input，step_id=confirm-requirements，prompt 一句"这是我理解的候选人画像，可以开始找了吗？"，选项两个："[推荐] 确认，开始找人" / "我要改某一处"（allow_custom，填写改哪里）。用户看到的只有画像；确认稿是 Agent 的规格，只存在于文件里。

用户选"我要改某一处"或在自定义里质疑某处时，只改确认稿被质疑的部分，写新版本文件，重新渲染完整画像再次请求确认。"没有补充""OK 吧"这类含糊回复视为未确认，同样重新呈现再问一次。

检索开始后用户补充需求时：写新版本文件，只在当前轮结束、下一轮 SearchPlan 编写前生效；纯约束型补充（如新增地点限制）只更新硬性筛选条件和评分项；版本切换后按 `references/scoring.md` 重评重建榜单。

完成标准：用户选了"确认，开始找人"，该版本文件冻结为当前需求版本；画像里每条必须满足、硬性条件、排除信号、关键判断都能在文件里找到对应。

**播报**："需求已确认，接下来检查浏览器和猎聘登录。"

把返回的 workflow_ref 传给 browser_run_workflow(task_id, workflow_ref)。登录、验证码和风控识别已编译进工作流；命中后浏览器显示窗口等待用户处理，按异常格式播报需要用户做什么，等用户处理完再继续。

**播报**："看了 X 家公司，其中 Y 家在猎聘上有足够多做这个方向的人，第 1 轮会优先从 Z 找。"（全部不可用时："这几家公司在猎聘上做这个方向的人都不多，第 1 轮先不限定公司。"）

### 7. 编写第 N 轮 SearchPlan

读当前需求版本文件（`<TASK_WORK_DIR>/wts/requirements/` 下 N 最大的 vN.json）和 `references/search-plan.md` 的字段、路径、限额契约，把需求版本拆为两路查询、站内筛选、硬性条件和语义评分项，写入契约规定的 iteration-N.json。

- **主路径查询（利用）**：第 1 轮的起手形态 = 主锚点 + 2 个不同词族的支持词 + 1 个公司词（按步骤 3.5 的规则选，没有则省去）。支持词里第二锚点算一个，其余优先核心技能、框架工具而非泛领域词；选哪两个由 Agent 判断。第 2 轮起形态由 Agent 按上一轮结果调：召回少就减到 1 个支持词或换公司词，召回多而噪音大就保留 2 个；支持词从活跃词中取不同词族，优先沿用带来新可推荐候选人的组合。
- **第二路查询（探索）**：第 2 轮起才有。有待试词时 = 主锚点 + 该待试词（**PRF 探针**）；否则 = 主锚点 + 1 个未试词族的支持词，优先级最高的备用词优先（**通用探索**）；两者都没有则本轮只有主路径。
- 一条查询内词族不重复；第二路与主路径本轮的非锚点词族不同；已发出过的词组合不再重复。关键词只来自当前需求版本的锚点、支持词、待试词或公司词。三轮全部服务于主池，title 范围、公司层、城市层中途保持不变。
- **site_filters**：取自硬性筛选条件中页面有控件的字段；岗位意图由关键词表达。
- **hard_filters**：全部明确的硬性筛选条件，以及排除信号中页面数据能验证的项。
- **semantic_criteria**：必须满足、加分项、排除信号，照录当前需求版本。
- **requirement_version**：从第 1 轮起写入当前已确认需求版本。同一版本只允许调整查询和合理的站内筛选，不得替换或删除 hard_filters、semantic_criteria。
- **decision_basis**：第 2 轮起保存截至上一轮的全部候选人原始评分、证据引用、首次评分轮次、PRF 判定和下一步；退出 Top 10 的候选人也保留。Builder 使用真实执行工作流中的计划快照校验，不能通过回改旧 iteration 文件绕过一致性检查。
- **exclude_candidate_refs**：已看台账里全部 candidate_ref（规则见 `references/seen-and-expand.md`）。第 2 轮起必填；第 1 轮只在合并了上一次台账时填。Builder 把它编译成卡片谓词，已看过的人不占本轮详情预算。

完成标准：iteration-N.json 已写入，两路查询、筛选和评分项都能回溯到当前需求版本；台账里的人都在 exclude_candidate_refs 里。

### 8. 编译本轮搜索工作流

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts/scripts/build_workflow.py" search --task-id TASK_ID --iteration N --task-work-dir "/ABSOLUTE/TASK_WORK_DIR" --plan-file "/ABSOLUTE/TASK_WORK_DIR/wts/search-plans/iteration-N.json"
```

默认使用拟人交互；需要即时操作时可显式加 `--interaction-mode direct`。`human` 模式由宿主执行渐进移动、逐字输入和有界滚动，不保证规避站点风控；执行 workflow_ref 时不能临时覆盖 Builder 固化的模式。

校验失败时按返回的错误原因原地修正同一个 iteration-N.json 并重新编译一次；仍失败则停止并说明。

### 9. 执行工作流

**播报**（执行前，必须预告）：本轮用哪几组关键词、预计几分钟、期间不会有新消息。例："第 2 轮开始，这轮用「AI Agent + LangGraph」和「AI Agent + RAG」两组词检索，预计 3–5 分钟，期间不会有新消息。"

然后调用一次 browser_run_workflow(task_id, workflow_ref)。整轮的搜索、筛选、抽卡、硬筛和详情采集都在这一次调用里由工作流完成。

### 10. 读取结果

先检查运行结果的 status、error_code、summary.metrics、summary.sections 和显式业务 summary。对 success 或 partial 结果，用 browser_read_workflow_result 读 details.primary，有第二路再读 details.secondary，每批最多 10 条；返回 `next_offset` 时用它继续读取，直到两路详情读完。不要因为已得到首批结果而重复从 offset 0 读取。partial 或任一路径 search.*.unsupported_filters 非空时再读 search。需要解释其他失败时再读 candidates 和 failures；空值按信息缺失处理，不用临时脚本强制转换。

读完立刻把 details 和 failures 里的每个人追加进已看台账 `<TASK_WORK_DIR>/wts/seen.json`（格式见 `references/seen-and-expand.md`）。

完成标准：两路 details 全部读完；partial 时已知道哪个站内筛选条件降级；台账已追加本轮打开的人。

**播报**：两组词各看到多少人、多少人进入详情、多少人通过硬性条件、几位是已看过而跳过的；站内筛选降级时在同一段里用一句白话说明哪个条件没能在页面上生效、后面会用简历内容补筛。

### 11. 隔离评分

仅对详情硬筛状态为 matched 或 unknown、且当前需求版本下尚未评分的候选人评分，跨轮按 candidate_ref 去重（以已看台账和最近 decision_basis 为准）。按 `references/scoring.md` 逐人评分，各人互相独立。先复用最近 `decision_basis` 中已经完成的评分，只补本轮新人；需求变更、新详情证据或明确的事实/计算错误才允许重评，并记录 correction_reason。沿用旧评分时把上一轮 candidate_scores 的条目**逐字复制**（含 evidence_summary、unknown、detail_ref），不润色、不缩写、不重排字段；Builder 提示某条被视为修订时，恢复原文再编译，这个过程不向用户播报。Builder 确定性计算总分、计数和 Top 10，退出榜单的历史评分继续保留。评完后把高分候选人的当前与过往公司按步骤 3.5 的规则加入目标公司池。

完成标准：本轮每位 matched/unknown 候选人都有评分记录；Top 10 与目标公司池已更新。

**播报**：本轮评了几人、新增几位可推荐、几位强匹配、榜单目前几人；目标公司池从高分候选人那里新增了几家（只说数量）。

### 11.3 校准门（只在第 1 轮）

第 1 轮评完分后、扩张或下一轮之前，让用户看一眼 Agent 的尺度，避免长任务跑到底才发现标准偏了。第 1 轮评分人数为 0 时跳过；第 2 轮起不再做。

先以普通文本输出 2 位判为值得推荐、1 位判为不推荐的候选人摘要（不足时有几位写几位），每位两行：第一行是去掉姓名和分数的画像（"某头部电商的 Agent 平台负责人，8 年，做过多智能体编排"），第二行是判断和一句依据（"我判断值得推荐：项目经历里有 LangGraph 落地" / "我判断不推荐：只做过对话机器人，没有工具调用经验"）。然后调用 request_user_input，step_id=calibrate，prompt 一句"这个尺度对吗？"，单选：

- "[推荐] 尺度对，继续找"
- "偏松，这样的人不该推荐"（allow_custom，填写哪一条要更严）
- "偏严，这样的人可以推荐"（allow_custom，填写哪一条可以放宽）

用户选偏松或偏严时，按步骤 4 的改稿流程写新需求版本，只改被点名的必须满足或加分项，重新渲染画像请用户确认；确认后按 `references/scoring.md` 把已评分候选人按新版本重评（correction_reason 写"校准门调整"），再继续。校准门不改变轮次和详情数量。

**播报**（校准通过后）："尺度确认了，接下来<扩张 / 第 2 轮>。"

完成标准：request_user_input 已发出并收到回答；有调整时新需求版本已确认、已评分候选人已重评。

### 11.5 轮内扩张（可选，可重复）

每轮的详情数量固定不变；扩张是评分（第 1 轮还要过校准门）之后的加餐。按 `references/scoring.md` 的**扩张门**判断本轮新人的质量：达标就留在本轮，从达标那条查询的首屏卡片里再挑一批人打开，而不是进下一轮；不达标直接进步骤 12。

具体挑谁、挑几个由 Agent 决定，规则和文件契约见 `references/seen-and-expand.md`：不全开，一次 5–10 人，优先卡片硬筛 matched、且和本轮高分候选人长得像的；已看台账里的人不挑。写 `iteration-N-expand-K.json`，编译：

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts/scripts/build_workflow.py" expand --task-id TASK_ID --iteration N --expansion K --task-work-dir "/ABSOLUTE/TASK_WORK_DIR" --plan-file "/ABSOLUTE/TASK_WORK_DIR/wts/search-plans/iteration-N-expand-K.json"
```

**播报**（执行前）："这轮开出来的人质量不错，我再从这一页挑 N 位打开看看，预计 X 分钟，期间不会有新消息。"

执行一次 browser_run_workflow，按步骤 10 读 `details.expand` 并追加台账，按步骤 11 只评新人（`detail_section` 写 `details.expand`，`scored_iteration` 写 N），播报本次扩张看了几人、新增几位可推荐。评完再判断一次扩张门：仍达标且本页还有值得挑的人，可以再扩（K+1），同一轮最多 3 次；否则进步骤 12。扩张不计入轮次，扩张评出的人和常规轮的人一起进下一轮的 decision_basis。

完成标准：每次扩张都有计划文件、运行结果、台账追加和评分记录；挑人依据在决策记录里。

### 12. PRF（伪相关反馈）：先试后晋升

支持词有五种状态：活跃词、备用词、待试词、已拒绝、无法判定。按 `references/prf.md`：先对本轮执行过的待试词按对账结果裁决（晋升 / 拒绝 / 保持待试 / 无法判定），再判断是否提议一个新的待试词。

### 13. 反思（只有建议权）

写一段不超过 5 句的反思：本轮两路各自的新增/重复情况；对现有活跃词和备用词提出激活 / 保留 / 降权 / 移除；对站内筛选字段提出保留 / 移除 / 新增（只限契约列出的字段）；从目标公司池中提议下一轮公司词（或提议不带），附一句依据；如认为可以停止，给出理由。反思可以记录对待试词的观察，但晋升、造词、改词表、写查询都是步骤 12 和 14 的权限。仍有未试的活跃词或备用词且榜单未达强池时，反思的停止建议无效。

反思和 Controller 是当前推理步骤，不是 Builder 子命令；Builder 不存在 `reflect` 子命令。

### 14. Controller 决策

**最大轮次** = min(轮次预算, 3)。**已完成轮数**是本轮在内、已经执行完步骤 7–14 的轮数；轮内扩张不改变轮数。开始第 N+1 轮的唯一条件是"已完成轮数 < 最大轮次"且下面的判定为继续：已完成 2 轮时 2 < 3，第 3 轮照常开始并完整执行。

Controller 是停止与下一轮关键词的最终决策者，按下列优先级判定：

1. 致命错误，或有外部副作用的动作效果未对账 → 终止或暂停，不报告终态。
2. 已完成轮数 ≥ 最大轮次 → 硬停。
3. 没有任何可执行查询（活跃词、备用词、待试词、仅锚点查询都已用尽）→ 以"词族耗尽"异常终止。
4. 质量门：强匹配 ≥ 3 或已成强池 → 可停；但有新候选人的轮次不足 2 且仍有未试词族 → 继续。强匹配 < 3 时：有未试词族 → 继续；没有 → 先放宽一次（激活备用词或换相邻写法）再允许低质量停止。
5. 救援（决定继续但没有可选活跃词族时，按序执行一步）：激活备用词 → 试跑已存在的待试词 → 仅主锚点查询（最多一次）→ 以"词族耗尽"停止。

继续时：输出下一轮主路径关键词（含下一个公司词，如有）与非地点筛选调整，对上轮反思逐条表态（接受 / 部分接受 / 拒绝），回到步骤 7。停止时：记录确定性停止原因——强匹配足够、新增候选不足、多轮无进展、达到最大轮次、词族耗尽、预算——进入步骤 15。

**播报**（每轮小结）：这轮两组词各带来多少新人、多少是重复（含扩张看的人）；累计可推荐和强匹配各几人；继续则说下一轮换哪组关键词及原因，停止则说一句原因并告知马上给出报告。待试词晋升、反思表态等内部记录留在决策记录里。

### 15. 终态报告

把最终 `decision_basis` 写到 `<TASK_WORK_DIR>/wts/final-decision.json`，其中 completed_iteration 是最后已完成轮次、next_action.action 为 report。执行 `settle --iteration N`，N 仍是最后已完成轮次，不新增第 N+1 轮。Builder 生成 `<TASK_WORK_DIR>/wts/final-report-data.json`；读取其中已核验的 Top 10 姓名、真实链接、分数、证据和 unknown，再按 `references/final-report.md` 补充现有市场洞察并渲染用户视图，不扫描结果目录或重新评分。

report.json 里要带 `seen_ledger_path`（本次台账的绝对路径）和 `not_recommended`（看过但没推荐的人数与原因汇总）；用户视图对没推荐的人只说数量和原因，不列个人。

完成标准：report.json 已写入；用户视图里每位 Top 10 候选人都有一行和真实链接。

### 16. 方向选择

终态报告输出后，调用 request_user_input，step_id=next-direction，用白话问一句"这个方向找完了，我这边还有几个方向，您看要不要从中选一个继续？"，单选，允许自定义：

- 每个备选方向一个选项，写成招聘用户听得懂的一句话（"从做过 XX 的人里继续找"）。没有备选方向时省去这一组，问句改为"这个方向找完了，接下来您想怎么安排？"。
- 固定加一个"以人找岗"选项："把这次找到的可推荐候选人拿去匹配平台上的其他岗位"。
- 固定加一个"先到这里"选项。
- 推荐一项并附依据：可推荐人数未达目标且有备选方向时推荐最接近主池的那个；已达目标时推荐"先到这里"。

这是本 Skill 的最后一个动作。用户的选择在本 Skill 之外处理：选了某个方向，那是一次新的寻访任务，从步骤 1 重新开始，主池即该方向；选了以人找岗，交给通用 Agent 的以人找岗功能，输入是本次的可推荐候选人；选了先到这里，结束。

完成标准：request_user_input 已发出，选项覆盖全部备选方向加两个固定选项，其中一项标了推荐。

## 决策规则

- 只有 JD 明确要求且渠道数据能够验证的条件才进入 hard_filters。语义匹配、潜力和偏好留给评分。
- 年龄、性别、学校名称、民族、婚育不参与检索、站内筛选、评分、排序、硬冲突判定或市场洞察归纳。用户提出此类要求时说明不予执行，其余条件照常处理。年龄是唯一有固定转换路径的一项：按步骤 3 的年龄转换专项问出真实关切，转成工作年限或职级；不估算年龄，也不用毕业年份、工作年限反推年龄。
- 只有简历可见的条件才进评分；面试核实项永远不影响分数、榜单和推荐结论，只在画像和终态报告里提示用户面试时核实。
- 零结果是有效的查询结果，进入正常的评分、反思和 Controller 决策；工具错误、超时或页面失败是失败，不记作零结果。
- 站内筛选降级（partial、unsupported_filters 非空）只是召回范围没缩小，同字段硬条件仍由工作流的卡片和详情硬筛执行；本轮照常评分，无需重跑。
- 未被容错块捕获的 TARGET_NOT_FOUND、WAIT_TIMEOUT、PAGE_STATE_NOT_RECOGNIZED，或工作流引用失效，都结束当前轮；只有调整搜索计划、更新 Skill 页面规则或恢复明确的人工作业状态后，才重新编译执行。
- 有外部副作用的动作出现网络错误、超时或效果未知时，先读取运行结果**对账**：已有明确观察则消费结果；证明未产生效果后才允许在下一轮重新编译执行；仍无法确定时暂停并说明。
- 只有前置或搜索工作流明确返回 login_required 时才判断为未登录；其他页面错误按各自的错误码处理。
